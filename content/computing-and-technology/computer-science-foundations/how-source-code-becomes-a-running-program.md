# How Source Code Becomes a Running Program

Somewhere between typing a line of code and watching a program respond, text made of English-like words, loops, and variable names turns into a stream of electrical signals a processor can act on directly. Almost nobody thinks about the machinery that makes that leap possible, which is more or less the point of building it well: a good compiler is supposed to be invisible, doing an enormous amount of careful translation and quietly getting out of the way. Pull back the curtain, though, and the process turns out to have distinct, well-defined stages, each solving a specific piece of a genuinely hard problem — how do you get a machine that only understands numeric instructions to do what a paragraph of human-readable code describes.

## Reading Before Understanding

The first stage, lexical analysis, does not try to understand the code at all. It simply breaks the raw text into meaningful chunks, called tokens: this sequence of characters is the keyword "if," this one is a variable name, this one is a number, this one is a punctuation mark separating two statements. It is roughly the same task a human performs, half-consciously, when reading a sentence and recognizing where one word ends and the next begins, without yet having parsed what the sentence as a whole means. A stray character that doesn't fit any recognized pattern — an unsupported symbol, an unterminated piece of text — gets caught right here, before the process has invested any effort in trying to make sense of the larger structure around it.

## Checking the Grammar

Tokens alone say nothing about structure; the next stage, parsing, arranges them according to the grammatical rules of the language, producing a tree-shaped representation, often called an abstract syntax tree, that captures how the pieces relate to one another. This is the same kind of work as diagramming a sentence in school, identifying the subject, the verb, and which clause modifies which — except here, "grammatical" means something far stricter than in natural language, because a program with even one mismatched parenthesis or missing punctuation mark usually cannot be parsed at all, rather than merely being parsed a bit awkwardly. This is where most of the syntax errors a programmer sees come from: not the lexer complaining about strange characters, but the parser reporting that the tokens, whatever they individually are, cannot be arranged into any valid structure the language's grammar allows.

## Making Sure It Actually Means Something

A program can be perfectly well-formed, grammatically speaking, and still be nonsense — adding a number to a piece of text in a language that forbids it, referring to a variable that was never declared, calling a function with the wrong number of arguments. Catching this class of problem is the job of semantic analysis, which walks the syntax tree with an understanding of what the language's constructs are actually supposed to mean. This is the stage responsible for type checking, which asks, for every operation in the program, whether the values involved are the kinds of things that operation is allowed to touch. It is also where variable names get resolved to the specific location in memory or scope they refer to, which matters enormously once a program has two different variables that happen to share a name in different parts of the code. A program that survives this stage is not just correctly punctuated; it is internally consistent, at least according to whatever rules the language enforces.

## Translating and Tightening

Once a program is confirmed to be both grammatically valid and meaningful, it still needs to become something a processor can execute, and most compilers do not make that jump in a single step. Instead, the syntax tree is typically translated into one or more intermediate representations — forms that are lower-level than the original source code but not yet tied to any specific processor's particular instruction set. This middle ground is where optimization happens: a compiler might notice that some calculation always produces the same result no matter what and simply compute it once in advance rather than recomputing it every time the program runs, or notice that an entire block of code can never actually be reached and quietly discard it, or reorganize a loop so that it does less redundant work on each pass. None of these optimizations are meant to be visible in the program's behavior — a well-optimized program is supposed to produce exactly the same results as an unoptimized one, only faster or smaller. Only after this reshaping does the final stage, code generation, translate the intermediate form into actual machine instructions, tuned to the particular processor the program is meant to run on, choosing specific registers and instructions in a way that earlier, more abstract stages deliberately avoided committing to.

## Compiling, Interpreting, and the Space Between

Not every language takes this exact path all the way to raw machine instructions ahead of time. A pure interpreter skips most of this pipeline's final commitment, instead reading through a program's structure and carrying out its instructions directly, one at a time, translating on the fly rather than producing a standalone machine-code file in advance — generally more flexible, and generally slower, since the same translation work is being redone every time a piece of code runs rather than once ahead of time. Many modern languages take a middle path, compiling source code not all the way to a specific processor's instructions but to a more portable intermediate form, sometimes called bytecode, which is then either interpreted or further compiled on the fly by a just-in-time compiler that watches the program actually running and pays special attention to optimizing whichever parts of it turn out to run most often.

This is why the same underlying set of ideas — tokens, grammar, meaning, translation, generation — shows up in some form no matter which route a particular language takes, even though the end results, an interpreted script, a compiled binary, and a bytecode-and-JIT hybrid, can feel like entirely different kinds of things to the person simply typing code and asking it to run. The stages exist because the problem they solve does not go away depending on which strategy a language designer picks; it only gets rearranged, split up differently, or shifted between the moment code is written and the moment it finally runs.
