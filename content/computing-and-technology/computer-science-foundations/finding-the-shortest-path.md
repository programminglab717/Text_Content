# Finding the Shortest Path

Ask a phone for driving directions across a large city and the answer arrives before you have finished putting the phone down. Somewhere behind that half-second, a road network with millions of intersections and tens of millions of road segments has been searched, weighed against current traffic, and reduced to a single blue line. The machinery that makes this possible was worked out mostly in the late 1950s and early 1960s, before anyone had a road network in digital form to search, and the same handful of ideas now sits underneath network routing, circuit layout, project scheduling, puzzle solvers, and the pathfinding of every character in every video game that has ever walked around a wall.

## What a Graph Strips Away

The first move is an act of deliberate forgetting. A graph keeps only two things: a set of nodes, and a set of edges connecting pairs of them. Everything else about the original problem — the width of the road, the color of the wire, the name of the airport — is either discarded or compressed into a single number attached to each edge, its weight. That weight might be distance in meters, or expected travel time in seconds, or dollars, or the probability of a link failing. The algorithms do not care which, and that indifference is exactly why the same code can route packets and route delivery vans.

Graph theory is usually dated to Leonhard Euler's treatment of the seven bridges of Königsberg in the eighteenth century, a puzzle about whether a walker could cross each of the city's bridges exactly once. Euler's insight was that the shape and size of the landmasses were irrelevant; only the pattern of connections mattered. Shrink each landmass to a dot, each bridge to a line, and the question becomes answerable by counting how many lines meet at each dot. That reduction — geometry thrown away, connectivity kept — is the move every graph algorithm still begins with.

Edges may be directed or undirected, which corresponds to one-way streets versus two-way ones, and this distinction matters more than it sounds. A directed graph can contain cycles that a walker can enter and never leave, and it can be acyclic, in which case the nodes can be laid out in an order where every edge points forward. That ordering, called a topological sort, is what a build system computes when it decides which files to compile first, and what a project planner computes when it figures out which tasks block which others. On an acyclic graph, finding longest and shortest paths becomes almost trivial: process the nodes in topological order and each one's best distance is already final by the time you reach it.

## Breadth First, and Why Unweighted Is Easy

If every edge costs the same — every road one block, every move one step — shortest paths fall out of a procedure so simple it barely deserves the name algorithm. Start at the origin. Visit all its neighbors. Then visit all of their unvisited neighbors. Then all of theirs. Because the search expands outward in rings of equal distance, the first time it reaches any node, it has reached it by a minimum number of steps, and recording which node you arrived from reconstructs the route. This is breadth-first search, and it needs nothing more than a queue and a set of already-seen nodes.

Its sibling, depth-first search, plunges down one branch as far as it can go before backing up, which makes it useless for shortest paths but excellent for other questions: whether a graph is connected, whether it contains a cycle, which strongly connected components it decomposes into. The two searches visit the same nodes with the same asymptotic cost and answer almost entirely different questions, purely by the difference between a queue and a stack.

## Dijkstra's Greedy Bet

Once edges have different weights, breadth-first search breaks. A path of two long edges can be worse than a path of five short ones, and the ring-by-ring expansion no longer corresponds to cost. Edsger Dijkstra's answer, which he later said he worked out in about twenty minutes over coffee in Amsterdam without pencil or paper, was to expand not in order of hops but in order of accumulated cost.

Every node gets a tentative distance, initially infinite except for the start, which is zero. Repeatedly pick the unfinished node with the smallest tentative distance, declare it settled, and then look at each of its outgoing edges: if going through this node reaches a neighbor more cheaply than that neighbor's current tentative distance, lower the neighbor's distance and record the improvement. Repeat until every reachable node is settled.

The reason this works rests on a single quiet assumption. When you settle the node with the smallest tentative distance, you are betting that nothing can reach it more cheaply later. Any alternative route would have to pass through some node that is still unsettled and therefore has a larger tentative distance, and then travel further along at least one more edge. If edges never have negative weight, travelling further can never reduce the total, so the bet always holds. The efficiency of the whole thing comes down to how quickly you can repeatedly extract the current minimum, which is what priority queues are for; a binary heap brings the total cost to something proportional to the number of edges times the logarithm of the number of nodes, which is fast enough that Dijkstra's algorithm remains the practical default fifty years on.

## When Weights Go Negative

The non-negativity assumption is not a technicality. Give one edge a negative weight and Dijkstra's greedy bet can fail outright: a node settled early and cheaply may turn out to be reachable more cheaply through a detour whose final edge subtracts cost. Worse, if a cycle has negative total weight, there is no shortest path at all, because you can always go around the loop once more and improve.

The Bellman–Ford algorithm handles negative weights by giving up on cleverness. Instead of choosing which node to process next, it simply relaxes every edge in the graph, over and over, a number of times equal to one less than the node count. After the first pass, all shortest paths of one edge are correct; after the second, all of two edges; and since no shortest path in a graph without negative cycles can use more edges than there are nodes, the process is guaranteed to have converged. Run the loop one extra time, and if any distance still improves, you have proved a negative cycle exists. That detection is not just a safety check — it is a useful result in its own right. Take a table of currency exchange rates, replace each rate with the negative logarithm of itself, and a negative cycle in the resulting graph is precisely a sequence of trades that returns more money than it started with. Bellman–Ford's edge-by-edge relaxation is also, in distributed form, how older internet routing protocols shared reachability information, each router telling its neighbors its current best distances and refining them in rounds.

## Giving the Search a Sense of Direction

Dijkstra's algorithm has one glaring inefficiency when you want a path between two specific points: it expands in every direction at once. Searching from Boston to Chicago, it will happily settle half of Maine before it gets going westward, because it has no notion that Maine is the wrong way. A*, developed at Stanford Research Institute in the late 1960s while trying to get a wheeled robot to cross a room, fixes this by adding a guess.

Alongside the known cost of reaching a node, A* adds an estimate of the cost remaining from that node to the goal, and expands whichever node has the smallest sum. On a road map, straight-line distance makes an excellent estimate: easy to compute, and never larger than the true road distance. That last property is what matters. If the estimate never overestimates — if it is, in the jargon, admissible — then A* is guaranteed to find a genuinely optimal path, while expanding a small fraction of the nodes that an undirected search would touch. Make the estimate zero everywhere and A* degrades exactly into Dijkstra's algorithm. Make it aggressive and inadmissible and the search gets faster still but starts returning paths that are merely good.

## Why Your Phone Doesn't Actually Run Dijkstra

Even A* is too slow for a continental road network answering thousands of queries a second, and production routing engines do something else entirely: they cheat in advance. A road network changes rarely, so it pays to spend hours preprocessing it once and then answer each query in microseconds. The dominant family of techniques, developed largely in the 2000s, contracts the network into a hierarchy — repeatedly removing unimportant nodes and inserting shortcut edges that preserve the shortest distances through them, so that a residential cul-de-sac gets absorbed into a shortcut while the interstate remains. A query then searches upward through the hierarchy from both ends, meeting somewhere in the middle, touching a few hundred nodes rather than a few million.

The result is that the algorithm your navigation app runs is not the one in the textbook, but it is only correct because the textbook one is. The shortcuts are built by proving they preserve exactly the distances Dijkstra's algorithm would have found, and the bidirectional search is validated against it. The 1950s procedure survives as the definition of the right answer, having been quietly replaced as the method of getting there.
