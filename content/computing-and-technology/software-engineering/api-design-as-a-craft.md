# API Design as a Craft

The function takes three arguments, all of them booleans, in an order nobody could guess on the first try. `resize(true, false, true)` compiles fine and does something — but what, exactly, without opening the source? Maybe the first flag preserves aspect ratio, the second allows upscaling, the third crops instead of padding. Maybe it's some other order entirely. The programmer calling this function has to either go read the implementation, which defeats much of the point of having a function at all, or guess and hope the test suite catches the mistake. This is what a bad interface costs: not that the underlying logic is wrong, but that using it correctly requires knowledge the interface itself refuses to provide.

An API — an application programming interface, though the term now covers everything from a single function signature to a company's entire public web service — is fundamentally a promise made to someone who hasn't shown up yet. It says: call this, in this shape, and you will get that back, and this promise will keep holding even after the code behind it changes. That last clause is what makes API design a genuinely different discipline from writing code that merely works. Code that works today can be rewritten tomorrow with no one the wiser, as long as the interface around it keeps its word. An interface that breaks its word, even while the code behind it becomes objectively better, has failed at the one job an interface has.

## Naming and the Principle of Least Surprise

Good interface design starts with a bias toward the boring choice. A method called `getUser` that also, as a side effect, creates a user record if none exists is lying about what it does, and the lie will eventually cost someone an afternoon, because "get" carries a promise of no side effects that every experienced programmer has absorbed from years of other interfaces behaving that way. Consistency compounds in the same quiet way naming does everywhere else in software: if one part of an interface calls something a "user" and another calls the identical concept an "account," every caller has to carry a small, permanent tax of translating between the two, forever, because nobody wants to be the one who renames a public API just for tidiness.

The deeper principle underneath all of this is sometimes called the principle of least surprise: an interface should behave the way a reasonable person, guessing from its name and signature alone, would expect it to behave. This sounds obvious and is routinely violated, usually in the name of flexibility. A function that accepts a dozen optional parameters, each subtly changing behavior in combination with the others, is flexible in the sense that it can do almost anything, and unusable in the sense that almost nobody can predict what it will do in a case they haven't tried yet. The craft is in resisting the urge to expose every possible configuration and instead finding the small number of shapes that cover almost every real need, cleanly, even if a rare case has to be handled some other way entirely.

## Leniency Has a Cost Nobody Sees Immediately

A famous piece of advice from the early design of internet protocols holds that a system should be conservative in what it sends and liberal in what it accepts — strict about producing well-formed output, forgiving about consuming slightly malformed input from elsewhere. It's good advice for keeping a fragile, decentralized network functioning day to day, and it has aged worse than it looked at the time, for a specific reason: whatever your implementation quietly tolerates, someone downstream will start relying on. If a service accepts malformed timestamps because the code happens to fall back gracefully, some client will eventually send malformed timestamps on purpose, because it worked once and nobody told them not to. An engineer at Google captured this pattern precisely enough that it now circulates as an informal law of its own: with enough users of an API, every observable behavior of the implementation, intended or not, becomes something somebody depends on. This is why a bug fix that tightens overly permissive behavior can break more callers than the equivalent new feature — the leniency itself became part of the contract the moment enough people leaned on it, whether or not it was ever documented.

## Versioning and the Myth of the Painless Upgrade

Every API eventually needs to change in a way that isn't backward compatible, and every strategy for handling that is a variation on the same underlying negotiation between the people maintaining the interface and the people depending on it. Semantic versioning tries to make the negotiation explicit by encoding a promise into the version number itself — a patch release changes nothing observable, a minor release only adds, a major release is allowed to break things — so that a caller can tell, from the number alone, how carefully they need to read the changelog before upgrading. This works reasonably well between organizations that both understand the convention, and works much less well the moment an interface has enough callers that "allowed to break things" collides with the reality that thousands of unrelated systems will need to update in lockstep, at their own pace, on their own schedules.

The practical answer most mature APIs converge on is a deprecation period rather than a hard cutover: the old shape and the new shape coexist for a while, the old one emitting warnings, until usage has dropped low enough that removing it stops being a catastrophe and starts being a cleanup. This is slower and more expensive to maintain than simply changing the interface and telling everyone to update, but it reflects an honest accounting of where the cost of change actually falls. An interface with many callers has effectively distributed a portion of its own maintenance burden onto every one of them, and a deprecation window is the closest thing to fair compensation for that burden — advance notice, and time.

## Errors Are Part of the Interface Too

It's easy to design the successful path of an API carefully and treat error handling as an afterthought bolted on once the happy path works, and this shows. A cryptic error code, an exception whose message describes an internal implementation detail rather than what the caller did wrong, a failure mode that's silent rather than loud — all of these are just as much a part of the interface as the function signature, because a caller has to handle them regardless of how little thought went into designing them. An interface that fails clearly, with an error that says specifically what was wrong and ideally how to fix it, saves every future caller the debugging session that a vague failure guarantees. Since errors are, by definition, encountered at the worst possible moment — under time pressure, usually in production — the quality of an interface's failure modes often matters more to how it's remembered than the quality of its successful ones.

Good API design, in the end, is a kind of applied empathy: an attempt to anticipate the state of mind of someone who knows less about this system than you do right now, reading unfamiliar documentation at an inconvenient hour, trying to get one specific thing done. The interfaces that hold up are the ones designed for that stranger rather than for the person who already understands every internal detail — which is worth remembering, since the stranger, more often than the designer expects, turns out to be the same person six months later, having forgotten most of what they knew.
