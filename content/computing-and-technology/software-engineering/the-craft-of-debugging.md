# The Craft of Debugging

The ticket says the nightly export produces an empty file about once a week. Not every night. Not on any particular day. The job reports success, the log shows the expected number of rows selected, and the file that lands in the bucket is zero bytes. Nobody has changed the export code in eight months.

This is the ordinary texture of debugging, and it is worth noticing how little the situation resembles the thing programming is usually described as. You are not building. You are doing diagnosis on a system that is lying to you — not maliciously, but because every layer is reporting what it believes rather than what is true, and one of those beliefs is wrong. The skill involved is closer to what a mechanic or an epidemiologist does than to design, and like those skills it is mostly method rather than talent. People who are fast at it are rarely people who guess well. They are people who eliminate possibilities in a deliberate order and refuse to skip steps.

## Reproduction Is Most of the Work

The first question is not "what is wrong" but "can I make it happen on demand." Everything downstream depends on the answer. Without reproduction you cannot tell whether a change fixed the problem or merely failed to trigger it, which is how teams end up shipping four consecutive fixes for the same bug and declaring victory after the one that coincided with a quiet week.

Reproduction is also where most of the diagnostic information hides, because the act of narrowing conditions is itself the investigation. A bug that happens once a week becomes a bug that happens every time the input set is empty, which becomes a bug that happens when the query returns zero rows because the upstream feed arrived late, which is no longer a bug in the export at all. Each narrowing step trades a vague failure for a specific one. When someone says they cannot reproduce an issue, what they usually mean is that they have not yet found the variable that matters — the timezone of the account, the second concurrent request, the customer whose name contains an apostrophe, the file that is exactly the size of one buffer.

Intermittent failures deserve special patience here, because randomness in a deterministic machine is always an illusion. Something is varying: thread interleaving, a hash iteration order that changes per process, the system clock crossing a boundary, an entry aging out of a cache, a retry that succeeds on the second attempt and hides the first. The useful move is to hunt for the hidden variable rather than to accept "flaky" as an explanation. Running the failing case in a tight loop, artificially slowing one participant, or pinning a clock will often convert a one-in-fifty failure into a one-in-one failure, and at that point the hard part is over.

## The Bug Is in the Assumption You Did Not Check

Every difficult bug lives inside something the programmer is certain about. This is nearly definitional — if you suspected that line, you would have looked at it already, and the bug would not be difficult. So the productive question during a stall is not "what else could be wrong" but "what am I taking for granted."

The list of things people take for granted is short and repeats across careers. That the code running is the code you are reading. That the config in the environment matches the config in the repository. That the library version is the one in the lockfile. That the build succeeded before the test ran. That the machine's clock is right. That the request reaching the service is the request the client thinks it sent. A surprising proportion of long debugging sessions end with the discovery that some part of this list was false — a stale container image, a shadowed dependency, a proxy rewriting a header — and the actual code was innocent the whole time. Verifying these is cheap and feels beneath you, which is exactly why it goes unchecked for three hours.

The discipline that guards against this is stating the hypothesis out loud before testing it, in a form that can be wrong. "The list is empty when it reaches the writer" is a hypothesis; you can print its length and find out. "Something's broken in the serialization layer" is a mood. Writing the prediction down first also prevents the most common self-deception in debugging, which is running an experiment, getting an ambiguous result, and retroactively deciding it confirmed what you already believed.

## Bisection in Space and in Time

Two searches do most of the heavy lifting, and both are binary.

The search in space asks where along the path the data stops being correct. You know the input is right at the beginning and wrong at the end, so you check the middle — the value as it leaves the parser, the payload as it crosses the network boundary, the row as it comes back from the database. Each check halves the suspect region. Ten checks will localize a fault in a thousand-step pipeline, which is why methodically placed observation beats staring at code that looks suspicious. The corollary is that you should place your probe at a boundary you can inspect cleanly rather than wherever your intuition is pointing, because a clean answer in a boring place is worth more than a murky answer in an interesting one.

The search in time asks when the behavior changed. If a system worked in March and fails now, the difference is in the set of commits between, and bisecting that set with an automated script — testing a midpoint, discarding half the history, repeating — will find the introducing commit in a number of steps proportional to the logarithm of the range. This works absurdly well and is underused, mostly because it requires a reliable automated check, which loops back to reproduction. It also has a quieter benefit: the guilty commit usually arrives with a message, an author, and a diff that explains the intent, which converts a mystery into a conversation.

When neither search is available because the failure only happens in production, the equivalent is differential diagnosis. You have a working case and a failing case; enumerate everything that differs between them and eliminate differences one at a time. Same code, different data. Same data, different machine. Same machine, different user. The answer is always in the difference list, and the list is always shorter than it feels at three in the morning.

## Instruments

The oldest instrument is printing a value, and no amount of tooling sophistication has retired it. It survives because it is trivially available, it works across process and machine boundaries, and it produces a durable record you can compare across runs. Its weaknesses are also real: it alters timing enough to hide race conditions, it requires you to know what to print before you know what is wrong, and every iteration costs a rebuild.

A debugger changes the economics by letting you ask questions you did not anticipate. You stop at a point and interrogate the whole world — every local, every field, the full call stack that explains how you arrived. For bugs whose cause is "something upstream handed me the wrong object," a stack trace at the moment of wrongness answers in seconds what printing would take an hour to triangulate. Conditional breakpoints handle the needle-in-a-haystack case: break on iteration eight thousand, when the id matches, when the value goes negative. Watchpoints, which trigger on a memory location changing rather than on a line executing, are the tool for the classic "who is corrupting this field" question, and most people who would benefit from them have forgotten they exist.

Below the application there is another tier that gets reached for too late. Tracing system calls will show you the file that was actually opened, which is not always the file the code names. Packet capture will show what really went over the wire, settling an argument between two teams in a way that reading either side's code cannot. A core dump preserves a crashed process's memory for inspection after the fact, which is the only option when the failure happened at four in the morning on a machine that no longer exists. In distributed systems, structured logs correlated by a request id across services are the equivalent of stepping through a single function: without that thread, every service's logs are a separate universe.

## What You Do After It Works

The fix is not the end of the work, and treating it as the end is how the same bug returns under a different ticket number.

Three things are worth doing while the context is still in your head. Write a test that fails without the fix — it is the only proof you have that you understood the cause rather than perturbed the symptom, and it prevents the regression from being reintroduced by someone who does not know why that line is shaped strangely. Look for siblings: a mistake made once in a codebase has usually been made three times, because whatever made it natural the first time was present the other times too. And ask what allowed it to reach production undetected, which is often a more interesting question than the bug itself. The missing validation, the error swallowed by a bare catch, the log line that reported success before confirming it — those are the conditions that made this bug expensive rather than cheap, and they are still there after the fix lands.
