# How a Name Becomes an Address

Type a familiar web address into a browser and, for a fraction of a second before anything loads, a small negotiation takes place that almost nobody ever sees. The name you typed is not something any router on the internet actually knows how to deliver packets to. Routers move packets toward numeric addresses — the internet protocol addresses that identify a specific network interface somewhere on the globe. Somewhere between your keystroke and the first packet leaving your device, that friendly name has to become a number, and the system performing this translation, quietly, billions of times a second worldwide, is the Domain Name System.

It's worth pausing on why this translation is necessary at all rather than just using numbers everywhere. Numeric addresses are efficient for machines and nearly impossible for people to remember reliably, especially now that the newer addressing scheme in wide use stretches to long strings of hexadecimal digits. Names solve the human side of that problem. But names also solve a second problem numbers can't: they let the underlying number change — a service moving to new hardware, a new data center, a different hosting provider — without anyone needing to update the name they type or the links they click. The indirection is the whole point.

## A Tree, Not a Phone Book

Early computer networks handled naming with something closer to a phone book: a single master file listing every machine's name and address, copied out to every computer on the network as things changed. That approach works for a few hundred machines and collapses completely as a network grows into the millions, since every change means redistributing the entire file everywhere. DNS, designed in the early 1980s largely by Paul Mockapetris, replaced the flat list with a hierarchy — a tree structure in which authority over any given portion of the namespace is delegated downward.

At the top sits the root, represented in a domain name by the invisible, unwritten dot after the final letter. Below the root are the top-level domains — the familiar .com, .org, and .net, along with the country-code domains like .uk or .jp and a large and growing set of others. Each top-level domain is itself managed by an organization responsible for it, which in turn delegates authority over individual second-level names — the "example" in example.com — to whoever registers them. That registrant can further delegate subdomains of their own. The upshot is that no single organization needs to know about every name on the internet; each layer of the tree only needs to know how to point toward the next layer down.

## The Resolver's Journey

When a device needs to turn a name into an address, it typically doesn't do the lookup itself. It hands the job to a recursive resolver — often run by an internet service provider, a company's own infrastructure, or one of several public resolver services — which does the actual walking of the tree on the device's behalf.

The device itself usually isn't running a full recursive resolver at all. Most computers and phones carry only a lightweight piece of software called a stub resolver, whose entire job is to package up the question and hand it off to whichever recursive resolver the device has been configured to use, then wait for the answer to come back. All of the actual tree-walking happens further upstream, which is why pointing a device at a different recursive resolver can sometimes noticeably change how quickly names resolve, even though nothing about the device's own software has changed at all.

If the resolver doesn't already have the answer cached from a previous lookup, it starts at the root. The root servers don't know the address of any particular website, but they know which servers are authoritative for each top-level domain, so the root responds with a referral: ask the .com servers. The resolver then asks a .com server, which likewise doesn't know the specific address but knows which servers are authoritative for that particular second-level domain, and refers the resolver onward again. Finally the resolver reaches a server that actually holds the answer — the authoritative server for that specific domain — and receives the numeric address it has been chasing. This entire chain, invisible to the person waiting for a page to load, usually completes in well under the time it takes to notice any delay at all.

There are, by design, only a small number of root server addresses — thirteen are defined, a limit set decades ago by the size constraints of an early DNS response packet — but each of those thirteen addresses is served today from a large number of physical machines scattered across the globe, using a routing trick called anycast that lets many machines share one address and lets each query get answered by whichever copy happens to be nearest. The number thirteen describes the addressing scheme, not the amount of hardware standing behind it.

## Why Nothing Feels Slow

If every single lookup required walking the entire tree from the root, the web would feel sluggish in a way it plainly doesn't. Caching is what saves it. Every answer that comes back from a DNS query arrives with a time-to-live value, a number of seconds for which the resolver is allowed to simply remember the answer and hand it out again without repeating the lookup. Popular domains get looked up constantly, so their answers stay warm in caches at resolvers all over the world, and the tree only actually gets walked in full for names nobody has asked about recently. This is also why changing a domain's address doesn't take effect instantly everywhere — resolvers holding an old, still-valid cached answer will keep handing it out until that entry's time-to-live expires, which is why administrators planning a migration typically shorten the time-to-live well in advance.

DNS records come in more varieties than the simple name-to-address mapping suggests. An A record maps a name to a numeric address; a CNAME record maps one name to another name, useful for pointing a subdomain at some other service's own name without needing to know or track its underlying address; an MX record tells the world which servers handle email for a domain; a TXT record holds arbitrary text, used today mostly for verification codes and anti-spam configuration. All of them live in the same hierarchical system and get resolved through the same chain of referrals.

## A System Built on Trust

For most of its history, DNS carried an assumption baked deeply into its design: that answers, once received, could simply be believed. A resolver asking a question had no built-in way to verify that a response genuinely came from the authoritative server it appeared to come from, rather than from an attacker who happened to guess or intercept the right identifying details and inject a forged answer first. This vulnerability, generally called cache poisoning, motivated the later development of DNSSEC, a set of extensions that let authoritative servers cryptographically sign their answers so a resolver can verify authenticity rather than take it on faith. Adoption of DNSSEC has been slow and uneven, partly because it adds complexity to a system whose great virtue for decades was simplicity, and partly because the incentive to deploy it falls on domain operators while much of the benefit accrues to the people looking up their names.

There is also an entire secondary industry built atop this naming system: domain registrars who sell names to the public, registries that operate each top-level domain, and a market in expired or desirable names that has, at various points, made a handful of short, memorable domains worth genuine fortunes. None of that commercial activity changes the underlying mechanics, but it's a reminder that a purely technical system for mapping names to numbers has, almost as a side effect, become a form of real estate.

## What the Tree Ultimately Hides

What DNS mostly demonstrates, working quietly underneath nearly every action taken online, is how much infrastructure can hide behind a single moment that feels instantaneous. A tree of delegated authority, a chain of referrals, a global caching system, and a small set of heavily replicated root servers all cooperate, unnoticed, every time a name needs to become a number, so reliably that the entire system is only ever noticed on the rare occasion it breaks.
